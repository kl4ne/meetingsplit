# Plan de terminación — MeetingSplit 0.8.19

Este plan es la referencia operativa del PR #7. Fecha inicial: 2026-11-27. Mantener `HANDOFF.md` actualizado. La terminación de la reparación de minutas, la compilación privada de QA y una publicación pública son tres hitos distintos.

## 1. Requisitos editoriales y límites de la solución

**Salida requerida:** resumen ejecutivo que permita entender el propósito, temas sustantivos y resultados sin leer toda la minuta; minuta detallada con prosa natural, temas agrupados coherentemente, acuerdos únicamente explícitos, tareas con descripción/responsable/plazo solo cuando consten, avisos diferenciados de propuestas, desacuerdos y pendientes, cifras y monedas sin cambios. El idioma elegido debe respetarse en la redacción principal. Las citas pueden permanecer en el idioma original, identificadas como tales; conservar referencias y timestamps en transcripción/JSON, no timecodes visibles ni tablas en la minuta. Si se solicitan ambos idiomas, conservar dos documentos/secciones independientes sin mezclar texto ni compromisos. No inventar participantes, fechas, responsables, decisiones, motivos, asignaciones de dinero ni urgencia. Distinguir enseñanza, explicación y recomendación general de una decisión o tarea. No transformar no aprobado en rechazado; no transformar el viernes / a más tardar el viernes / antes del viernes en equivalentes. Respetar avisos de abril y del mes en curso como eventos distintos.

**Fidelidad:** las citas originales son inmutables; las comprobaciones de expresiones regulares, coincidencia literal, anclas léxicas, cobertura de IDs y esquemas JSON son filtros conservadores, no certificación semántica. Un documento puede aprobar todas esas comprobaciones y seguir siendo incorrecto, demasiado genérico o repetitivo. `review_required: true` es deliberado. Nunca borrar una advertencia para hacer verde CI. Una corrección de clasificación debe mostrar la cita que la justifica, y preservar el resto. No sustituir una traducción rechazada por una descripción previamente identificada como falsa/incompleta. No quitar contenido único mediante una heurística de similitud. No exigir que el modelo invente registros estructurados para conversación sin resultados; distinguir omisión real de ausencia de acuerdos.

**Restricciones:** utilizar Qwen3.5:9b (`qwen3.5:9b`), digest `56671c2ab9385f9cfcb404638e32cd62d88e3501d44822208363c010179a3c90`, Ollama 0.40.18 para comparaciones controladas. La impresión histórica favorable en chat interactivo con otros modelos no es un A/B controlado. El runtime de Linux usado en QA tiene archivo oficial fijado SHA-256 `b82649006cb5b54ed1237fa2d1a26a7f939a4fd03150033759acbff7ff315adf`. El runtime CPU de GitHub no mide el rendimiento de RTX 4070. El original de 0.8.18 en ASUS reportó 1529.34 s para 16,037 palabras / 270 filas / 29 bloques, cuatro decisiones y dos tareas, ocho lagunas editoriales y 15 fallbacks narrativos; estos datos proceden del handoff anterior, no de una repetición independiente en este entorno. No afirmar disponer de sus archivos exactos.

## 2. Arquitectura actual y dónde tocar

| Archivo | Responsabilidad y restricciones |
|---|---|
| engine/summarize.py | Orquestación: bloques con IDs, caché de extracción, reintentos acotados, extracción, reconciliación, síntesis, presentación, trazas opcionales. `localized_editorial` usa extracción + síntesis + traducción necesaria, no doble redacción/revisión. `reviewed` conserva camino anterior para comparar. |
| engine/minutes_evidence.py | Validación estricta de citas, cantidades, clasificación, fuente explícita, reintento selectivo, render Markdown, cobertura estructurada y repetición literal. Evitar cambios que eliminen alertas. |
| engine/minutes_brief.py | Agrupación de temas, validación, reintento acotado de temas rechazados. Los IDs válidos no demuestran que se hayan cubierto todos los temas. |
| engine/minutes_narrative.py | Camino histórico de borrador/revisión: validación de párrafos, recuperación selectiva, anclas; no reactivar sin evidencia de beneficio editorial. |
| engine/minutes_localization.py | Selección de traducciones imprescindibles, copia de presentación, validación de idioma/monedas/nombres/plazos, restitución de relación de día de semana en casos muy estrechos. No tocar fuente original; si falla, advertir. |
| engine/minutes_overview.py | Resumen extractivo acotado de temas y resultados verificados, orden cronológico, conserva nombres y plazos cuando faltan. Aún no es una síntesis semántica profesional global. |
| engine/minutes_theme_presentation.py | Contabiliza líneas largas repetidas literalmente y separa propuestas/pendientes cuyo evento completo ya se presenta en su sección. Registra los índices originales. |
| engine/job.py | Integración real de estrategia `localized_editorial`, recuperación de minutas, manifest, cancelación, preservación de audio/transcripción/ZIP. `needs_review` si hay registros review, lagunas reales, fallbacks o traducción rechazada. No cambiar privacidad ni distribución. |
| qa/minutes_editorial_ab.py | Fixture corto bilingüe, referencia y diez criterios de lectura; A/B directo vs aplicación y trazas. Direct API no equivale a chat interactivo. |
| qa/minutes_long_acceptance.py | Fixture histórico repetitivo de 11 bloques; el main() tiene un digest antiguo, NO ejecutar como aceptación moderna sin adaptarlo. Usar fixture()/score() con runtime fijado en harness separado. |
| tests/test_minutes_*.py, tests/test_functional_repair.py | Regresiones, controles negativos y recuperación real de checkpoint simulado. No actualizar expectativas para ocultar fallos. Los cambios de mocks se justificaron para soportar traducción y frases válidas. |

La guía `docs/Guia_Owll_y_Minutas_para_Ollama.md` sigue incluida. Es grande y se añade a prompts de extracción y síntesis; sus indicaciones genéricas pueden competir con los requisitos de cada etapa. Si se propone optimizar prompts, medir con una comparación controlada; no recortar por intuición ni modificarla sin regresiones. `qa_trace` solo se activa en QA sintética explícita, no en desktop normal, ni logs, ni ZIP del usuario. Toda inferencia local utiliza loopback y conserva cancelación/CPU fallback.

## 4. Método de continuidad y trabajo seguro

Al iniciar cada turno: consultar estado real de Actions, no repetir la misma prueba por rutina. Cuando hay una ejecución en curso, solo avanzar en tareas independientes o preparar ramas aisladas. Las actualizaciones de la misma rama pueden cancelar CI por concurrencia. Mantener PR #7 como rama de integración; ramas `qa/*` son pruebas, no fusionar workflows experimentales automáticamente. Antes de actualizar ref, comprobar HEAD y parentesco; usar expected_sha. No forzar push, no borrar ramas ni cambiar main sin autorización. Para fallos de código, crear prueba de regresión exacta y controles negativos. No presentar una reparación como integrada hasta comprobar el commit; distinguir candidato aislado, CI pasado, replay pasado, inferencia real, evaluación editorial, binario y prueba hardware.

El conector GitHub permite leer archivos/commits/PRs, jobs, logs, artefactos y crear ramas/árboles/commits; usar las acciones disponibles en el nuevo chat y revisar sus esquemas. Si no hay dispatch, un workflow de QA limitado a su rama y archivo disparador puede iniciar por push. Evitar usar tokens de usuario en código o logs. `download_workflow_artifact` proporciona archivo ZIP; inspeccionar bytes reales en entorno disponible, no inferir contenido por nombre. No guardar links temporales firmados en documentos. Los artefactos de Actions caducan (muchos 7–14 días); IDs no garantizan permanencia. Conservar checks, resúmenes de defectos y fixtures en repo. Si falta un artefacto, registrar la limitación y recuperar de una copia autorizada o crear una prueba focalizada.

El usuario prefiere español, avances verificables, evitar gasto y tiempo innecesarios y no recibir falsas promesas de trabajo en segundo plano. GitHub Actions puede seguir sin el chat, pero el asistente no trabaja entre turnos. No pedir al propietario que ejecute ASUS hasta que se cumplan criterios de fuente y portable, salvo necesidad documentada del fixture o prueba final. Si cambia una restricción, reflejarla en HANDOFF y en plan. Ante fin de contexto, guardar el SHA, tarea concreta siguiente, evidencias, errores, decisiones y blockers para que otro chat prosiga sin empezar de cero.
